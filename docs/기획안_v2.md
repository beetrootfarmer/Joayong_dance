# 춤추자! 조아용~ — 크로마키 실시간 합성·송출 체험

기획안 v2.0 · 작성일 2026년 9월 24일 · 이전 버전: `조아용_크로마키_체험_기획안.pdf` (v1.0)

> v2.0 변경 요약: 제어 로직을 별도 Node.js 앱 + obs-websocket 소켓 구조에서 **OBS 내장 Python 스크립트**로 전환했고, 곡 선택·시작 단계에 **제스처(동작 인식) 조작**을 추가했습니다. 동의 절차는 그대로 스태프가 사전에 받는 방식이며, 제스처가 실패할 때의 운영자 우회 경로를 명시했습니다.

---

## 1. 기획 배경과 목적

행사장의 마스코트 체험은 대부분 인형탈과 사진을 찍고 끝납니다. 참여자가 남기는 것은 각자의 휴대폰 속 사진 한 장이고, 그 자리에 없던 사람에게는 행사가 전달되지 않습니다.

이 프로그램은 참여자를 구경하는 사람에서 콘텐츠에 등장하는 사람으로 바꿉니다. 크로마키로 합성된 시민이 조아용과 함께 춤추는 장면이 만들어지고, 그 장면이 실시간으로 유튜브에 송출됩니다.

| | |
|---|---|
| **참여 경험** | 자기 모습이 화면 속 조아용 옆에 나타나는 순간이 체험의 핵심 |
| **콘텐츠 확산** | 체험 장면이 그대로 라이브 방송이 되어, 별도 촬영·편집 없이 기록과 홍보물이 동시 생성 |
| **캐릭터 활용** | 댄스 영상을 한 번 제작하면 이후 행사에서 곡만 추가해 반복 활용 |

---

## 2. 서비스 개요

화면은 세 겹으로 구성됩니다: 배경(조아용 댄스 영상) → 인물(그린스크린 크로마키 합성) → 오버레이(곡 제목·카운트다운).

| 출력처 | 내용 | 음원 |
|---|---|---|
| 유튜브 라이브 | 합성된 화면 실시간 송출 | 차단 |
| 부스 모니터 | 합성된 화면 (참여자가 보며 춤추는 용도) | 스피커로 재생 |
| 로컬 녹화 | 합성 결과만 저장. 카메라 원본은 저장하지 않음 | 차단 |

음원을 송출에서 제외하는 이유: 상업 음원이 포함된 라이브는 저작권 검출로 음소거되거나 중단될 수 있습니다. 자체 제작 영상 사용을 전제로 합니다.

## 3. 시스템 아키텍처 (v2 — 핵심 변경)

### 3.1 왜 바꿨는가

기존 v1 설계는 별도 Node.js "제어 앱"이 obs-websocket(소켓)으로 OBS와 통신하는 구조였습니다. 검토 결과 다음 이유로 변경했습니다:

- 소켓 연결은 끊김·재연결·상태 재동기화라는 부가 복잡도를 만듭니다. PRD v1의 필수 기능이었던 "자동 재연결", "연결 상태 표시"는 애초에 소켓이 없으면 존재할 필요가 없는 문제입니다.
- OBS는 자체 Python 스크립팅 엔진(obspython)을 내장하고 있어, 씬 전환·미디어 소스 교체·재생 종료 감지를 **같은 프로세스 안의 함수 호출**로 처리할 수 있습니다. 네트워크도, 소켓도, 별도 프로세스도 필요 없습니다.

### 3.2 구성 요소와 통신 방식

```
                     ┌─────────────────────────────────────────┐
                     │              OBS Studio 프로세스           │
                     │                                           │
  참여자 브라우저 ──HTTP──▶  Browser Source (곡선택 씬)             │
  (Next.js 페이지,        │      = 아래 gesture-ui 페이지            │
   카메라+MediaPipe)      │                                           │
                     │  ┌─────────────────────────────────┐    │
  gesture-ui 서버 ◀───────┤  joayong_control.py (obspython)   │    │
  (Next.js, localhost)  │  - 상태머신 (idle→consent→...)     │    │
  선택 확정 시           │  - 씬 전환, 미디어 소스 교체          │    │
  command.json 기록  ──▶│  - 텍스트 소스 갱신 (제목/카운트다운)  │    │
  (파일, 소켓 아님)      │  - command.json 폴링 (타이머)        │    │
                     │  - 세션 로그 기록 (JSONL, 개인정보 없음) │    │
                     │  - 운영자 단축키 처리                  │    │
                     │  └─────────────────────────────────┘    │
                     └─────────────────────────────────────────┘
        ▲                                    │
   USB 웹캠 (제스처 전용,              유튜브 라이브 / 로컬 녹화 / 부스 모니터
   OBS 캡처카드와 별도 장치)
```

**통신 방식 정리:**

| 연결 | 방식 | 비고 |
|---|---|---|
| 제어 로직 ↔ OBS | obspython in-process 함수 호출 | 소켓 아님. obs-websocket 라이브러리 미사용 |
| gesture-ui(Next.js) → 제어 로직 | 로컬 `command.json` 파일 쓰기 + 스크립트가 타이머로 폴링 | 소켓 아님. 상태 없는 1회성 이벤트만 기록 |
| 참여자 브라우저 → gesture-ui 서버 | `http://localhost:포트` HTTP 요청 | 지속 연결이 아닌 요청-응답. 곡선택 화면 표시 + 선택확정 API 호출 1회 |

**Next.js가 "예외로 허용된 가벼운 서버"인 이유**: 상태를 유지하지 않고(stateless), 정적 페이지 서빙과 파일 쓰기 API 하나만 담당합니다. 이 서버가 죽어도 OBS 스크립트 쪽 상태머신·카운트다운·로그는 영향받지 않으며, 운영자가 즉시 단축키로 우회할 수 있습니다.

### 3.3 설계 판단 (갱신)

| 판단 | 이유 |
|---|---|
| 제어는 OBS 내장 Python 스크립트가 담당 | 소켓·재연결·별도 프로세스 관리 복잡도 제거. OBS가 켜져 있으면 항상 함께 존재 |
| 제스처 UI는 Next.js, OBS Browser Source로 표시 | 카메라 미리보기·애니메이션 등 표현력이 필요한 화면에 한정. 이미 검증된 MediaPipe 구현 재사용 |
| 카운트다운/상태표시는 네이티브 OBS 텍스트 소스 | 세션 내내 살아있어야 하는 표시는 Next.js 생존 여부와 무관하게 동작해야 함 |
| gesture-ui ↔ 제어 스크립트는 파일 폴링 | 소켓을 만들지 않으면서 두 런타임을 연결하는 가장 단순한 방법 |
| 진행 상태는 제어 스크립트가 단독 관리 | 한 곳이 상태를 관리하고 나머지(오버레이, gesture-ui)는 표시만 담당 |
| 송출 시작·중지는 OBS에서 직접 | 운영 중 실수로 방송이 중단되지 않도록, 스크립트는 송출 상태를 표시만 함 |
| 영상은 PC 내부 저장 | 재생 중 버퍼링 방지 |

## 4. 체험 운영 시나리오 (v2)

한 팀의 체험은 약 3~4분이며, 운영자 1명 + 안내 스태프 1명이 진행합니다.

1. **대기** — 부스 모니터·송출 화면에 대기 화면. 스태프가 프로그램을 안내.
2. **동의 확인 (입장 시, 스태프)** — 초상권 송출 동의를 태블릿 또는 종이로 받습니다. 만 14세 미만은 보호자 동의 포함. **동의는 제스처로 받지 않습니다** — 누가 동의했는지 기록이 남지 않고, 3m 거리에서 화면 속 동의 문구를 읽게 하는 것도 현실적이지 않기 때문입니다. 동의 확인 후 스태프/운영자가 단축키로 "동의 완료" 상태를 표시합니다.
3. **곡 선택 (제스처 우선, 운영자 우회 가능)** — 참여자가 그린스크린 앞에서 화면 속 버튼 위에 손을 올려 일정 시간(dwell) 유지하면 선택됩니다.
   - **8초 이상 진행이 시작되지 않으면** 오버레이에 "운영자에게 말씀해주세요" 안내가 자동 표시되고, 안내 스태프가 개입해 운영자가 단축키(1~9)로 직접 선택합니다.
4. **카운트다운** — 시작 버튼도 동일한 dwell 방식. 실패 시 운영자가 `Space`로 직접 시작. 댄스 화면 전환 + 카운트다운 표시.
5. **재생** — 영상 재생, 참여자가 함께 춤추는 장면이 그대로 송출.
6. **종료** — 종료 메시지 후 대기 화면 자동 복귀. 다음 팀 진행.

**운영자 우회 원칙**: 제스처와 단축키는 항상 **동일한 내부 함수**(`select_song(id)`, `start()`)를 호출합니다. 우회 경로가 별도로 구현되어 테스트되지 않은 채 방치되는 일을 막기 위함입니다.

## 5. 제스처 인식 설계

### 5.1 왜 동그라미 제스처가 아니라 "화면 속 버튼" 방식인가

원(circle) 등 형태 기반 제스처는 조명·각도에 인식률이 크게 흔들리고, 참여자에게 설명하는 데 시간이 걸리며, 팔을 계속 들고 있어야 해서 대기줄이 길어질수록 참여자가 지칩니다. 화면에 버튼을 띄우고 손을 잠시 올려두는 "호버(dwell)" 방식은 Kinect 시절부터 검증된 패턴이고 설명 없이 바로 이해됩니다.

### 5.2 인식 방식

- **1차 구현**: 이미 확보된 그린스크린을 활용한 픽셀 카운팅(또는 팀에 기존 검증된 MediaPipe 구현이 있다면 그대로 재사용). 버튼 영역 안의 전경(비-그린) 픽셀 비율을 계산합니다. 그린 판정은 RGB 고정값이 아닌 **HSV(색상 범위)** 기준으로, 그림자·주름 진 그린스크린을 사람으로 오인하지 않도록 했습니다. 판정 흐름과 HSV 전환 근거는 [`gesture-detection.md`](gesture-detection.md) 참고.
- **히스테리시스 적용**: 임계값 하나로 판정하면 경계에서 깜빡입니다. 예) 55% 이상이면 진행 시작, 40% 밑으로 떨어져야 리셋.
- **최소 dwell 시간**: 1.5~2초. 지나가는 사람의 팔 흔들림으로 오발동하지 않도록.
- **좌우 반전 필수**: 반전하지 않으면 참여자가 자기 손 움직임과 화면 방향이 반대로 느껴져 헤맵니다.
- **버튼은 크고 적게**: 3m 거리 조작 기준 화면 폭의 1/4 정도. 곡이 많으면 2~3개씩 페이지 전환.
- **다인원 처리**: 픽셀 카운팅은 누구 손인지 구분하지 못합니다. 곡선택 단계에서는 바닥 표시로 대표 1인만 프레임에 들어오도록 안내.

### 5.3 카메라 분리

OBS가 캡처카드를 점유하면 브라우저가 같은 장치를 열 수 없습니다. → **제스처 전용 USB 웹캠을 별도로 설치**합니다 (참여자 방향, OBS 카메라와 독립). 설치 시 버튼 영역 좌표를 1회 보정합니다.

### 5.4 화면 표시 방식과 리스크

gesture-ui(Next.js) 페이지를 OBS의 Browser Source로 곡선택 씬에 배치하는 것을 권장합니다. **검증 필요 리스크**: OBS Browser Source(내장 CEF)가 `getUserMedia`(카메라 접근)를 안정적으로 지원하지 않는 버전이 있습니다. 기술 검증 단계(§7 1단계)에서 반드시 확인하고, 실패 시 별도의 실제 브라우저 키오스크 창으로 대체합니다.

## 6. 개발 범위

| 기능 | 내용 | 우선순위 |
|---|---|---|
| 곡 목록 관리 | JSON 설정 파일로 곡·영상 관리, 스크립트 로드 시 파일 존재 검사 | 필수 |
| 동의 상태 반영 | 스태프가 사전 확인한 동의를 단축키로 표시. 동의 전 곡 선택 잠김 | 필수 |
| 곡 선택과 준비 | 영상 교체, 첫 화면 대기, 준비 완료 후 시작 가능 | 필수 |
| 카운트다운과 재생 | 화면 전환, 정확한 시점 재생 시작 | 필수 |
| 종료와 자동 복귀 | 재생 종료 감지(media_ended) → 종료 메시지 → 대기 복귀 | 필수 |
| 운영자 강제 제어 | 정지, 처음부터 다시, 대기 전환, 세션 초기화 (전부 단축키) | 필수 |
| 상태 표시 | 송출·녹화 여부, 경과 시간, 누락 프레임 (연결 상태 항목은 소켓 제거로 불필요해짐) | 필수 |
| command.json 폴링 | gesture-ui 이벤트를 단축키와 동일한 내부 호출로 처리 | 필수 |
| 제스처 인식 (곡선택/시작) | 전용 웹캠 + dwell 방식, 히스테리시스 적용 | 권장 (재미 요소, 운영자 우회가 필수) |
| 제스처 타임아웃 안내 | 일정 시간 진행 없으면 오버레이에 안내 표시 | 필수 |
| 오버레이 디자인 | 대기 화면과 같은 톤의 곡 제목/카운트다운 (네이티브 텍스트 소스) | 권장 |
| 운영 로그 | 세션별 곡, 동의 처리 시각, 진행 시각, 오류. 개인 식별 정보 없음 | 권장 |
| 다음 순서 예약 | 진행 중 다음 참여자 곡 미리 지정 | 선택 |

**이번 개발에서 제외**: 얼굴 추적/조아용 탈(비동의 참여자용, 2차 개발), 방문객 직접 조작 키오스크(수요 확인 후 검토), 다중 카메라·다중 영상(싱크 관리 부담).

## 8. 운영 계획

### 8.1 장비 구성

| 장비 | 수량 | 비고 |
|---|---|---|
| 송출 PC (데스크탑) | 1 | 하드웨어 인코더 필수. 영상 출력 2개 사용 |
| 운영자 모니터 | 1 | OBS 표시 |
| 부스 모니터·스피커 | 각 1 | 참여자가 보며 춤추는 용도 |
| 카메라, HDMI 캡처카드 | 각 1 | OBS용. 화면 표시 없는 HDMI 출력 지원 카메라 |
| **USB 웹캠 (제스처 전용, 신규)** | **1** | **참여자 방향, OBS 캡처카드와 별도 장치. 설치 시 버튼 영역 좌표 보정 1회 필요** |
| 그린스크린, 조명 | 1식 | 배경과 인물을 따로 비추는 조명 2~3개 |
| UPS, 전용 멀티탭 | 각 1 | 정전 대비 |
| 유선 LAN, 백업 회선 | 1식 | 유선 우선, 백업 LTE |
| 백업 노트북 | 1 | 동일 설정 미리 구성 |

### 8.2 부스 구성 시 확인 사항

- 참여자 위치를 바닥에 표시 (댄스용 + 곡선택 단계용 별도)
- 초록색 옷 입은 참여자는 투명 처리되므로 사전 안내
- 송출 PC는 통풍 확보, 부스 모니터는 직사광선 회피

### 8.3 인력

| 역할 | 담당 |
|---|---|
| 운영자 1명 | 단축키 조작, 진행 안내, 장애 대응, 제스처 실패 시 즉시 개입 |
| 안내 스태프 1명 | 동의서 접수, 대기열 관리, 참여자 위치 안내, "대표 1인 선택" 안내 |

## 9. 위험 요소와 대응 (갱신)

| 상황 | 영향 | 대응 |
|---|---|---|
| 음원 저작권 | 라이브 음소거/중단 | 송출 음원 차단, 자체 제작 영상 전제 |
| 초상권 | 동의 없는 얼굴 공개 송출 | 입장 시 스태프가 동의 확보. 동의 전 곡 선택 잠김 |
| 제스처 오인식/미인식 | 참여자 진행 불가, 대기 지연 | 8초 타임아웃 → 운영자 단축키 우회 (동일 내부 함수) |
| gesture-ui(Next.js) 서버 다운 | 곡선택 화면만 영향, 나머지 무관 | 상태 없는 서버라 제어 스크립트·로그·재생에 영향 없음. 운영자 우회로 즉시 복구 |
| OBS Browser Source 카메라 미지원 | 제스처 UI 표시 불가 | 별도 브라우저 키오스크 창으로 대체 (기술검증 단계에서 사전 확인) |
| 인터넷 끊김 | 송출 중단 | 합성·부스 화면·녹화는 유지. 백업 회선, 사후 업로드 |
| OBS 자체 오류/크래시 | 전체 중단 (제어 스크립트가 OBS 내부에 있으므로 별도 복구 불가) | 백업 노트북 준비, 수동 재시작을 운영 절차로 수용 |
| 장비 고장 | 운영 중단 | 백업 노트북, 케이블·캡처카드 예비 확보 |
| 정전 | 전체 중단 | UPS로 안전 종료 시간 확보 |
| 성능 저하 | 화면 끊김 | 1080p 30fps 기준, 연속 운영 시험에서 확인 |
